# Role-Bounded Factory Work

Planning/build/review/verify are workflow responsibilities, not built-in grants.
Resolve the actual assigned role revision and signed policy for the specific
organization, endpoint, workspace and task before using any action tool.

| Responsibility | Minimum useful authority | Required boundary |
| --- | --- | --- |
| Plan | Read approved task/context and shared vocabulary | No implied code write, dispatch, role change or paid model authority |
| Implement | Explicit task-scoped write/tool/network authority | Stay inside approved paths; keep actual diff/tool/effect receipts; protected effects require current decisions |
| Review | Read-only approved context and bounded answer capability | No source writes or inherited setup approval; do not include secrets or unrelated history in answers |
| Verify | Authorized independent test/evidence access | Keep held-out graders inaccessible to the Implementer; report failures without rewriting historical evidence |

For a peer question, first discover only permitted roles/endpoints for the
selected binding. Target a verified endpoint and named session when required.
Bind the question to its task and bounded context, category, disclosure, expiry
and finite budget. Observe the actual answer and follow-up continuity; queued,
delivered and acknowledged are not answered. Do not broaden role or source
authority when a target is unavailable.

For a governed action, retain the original state/evidence reference, decision,
receiver acknowledgement, observed effect and independent outcome. Preserve
release, block, escalate and withhold as distinct outcomes. A refused action must
have no protected effect. Message delivery or a device poll is not enforcement.

For learning, use the selected policy's actual consent, observation, independent
validation, canary/control and spending requirements. Each worker's durable count
is separate. At every qualified automatic 100 boundary, retain the intake,
analysis/candidate, validation, signed recipient-bound distribution, activation
and subsequent-use references. Repeated boundaries, deduplication, interruption
and rejected-candidate rollback must remain auditable. Never replace this with a
global count, an imported transcript or a manually issued skill.

Code self-improvement by the factory is a distinct governed change/review/test/
release/later-task-use workflow. Skill distribution alone does not prove it.
Use the existing change and release owners; this setup skill confers no merge,
deployment, financial or infrastructure-maintenance authority.

## Negative Cases

- A review-only agent asked to edit source returns the effective-policy denial;
  it neither modifies files nor asks a privileged teammate to perform the denied
  operation under another identity.
- A knowledge-only member without GitHub access uses the separately qualified
  knowledge route or reports its precise missing contract. It does not register
  a fake source repository, demand personal GitHub or copy a developer credential.
- A provider with only asset-discovery evidence is labelled accordingly; no
  named-session, capture, task or restart claim is inferred.
- An expired reference or wrong-account approval stops. A new attempt requires
  its own supported admission after reconciling the old effect; no replay.
- A manual skill installed successfully is not accepted learning or observed use.
- A deterministic local check may run without inference; model-backed analysis
  still requires its applicable model and budget authority.
