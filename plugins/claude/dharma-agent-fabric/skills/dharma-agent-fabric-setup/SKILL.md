# Set Up Dharma Agent Fabric

Operate the customer's supported client yourself. The normal recipient action is
reviewing the matching device in the browser, not running terminal commands,
pasting a private grant, fixing a keyring or sharing credentials. A copied prompt
or this skill is not permission to enroll, widen source access or start paid work.

## Select the Actual Route

1. Establish the requested portal, organization, intended member, client/provider
   and purpose from the authorized request or portal selection. Do not derive the
   Dharma recipient from the provider subscription account. Preserve an existing
   enrollment and original session instead of creating a replacement to fix it.
2. Use the portal's exact qualified CLI and supported public installation route.
   Verify the release, runtime requirements and artifact integrity before running
   it. Never choose `latest`, copy another client's authentication, invent harness
   markers or install a second client to evade a denial.
3. Read [Client Routes](references/client-routes.md) for the actual capabilities
   needed by this client. A provider name in a catalog does not qualify enrollment,
   enforced tasks, capture or restart for that provider.
4. If the qualified release advertises the interactive first-run entry, launch
   bare `dharma` in the genuine interactive client. It must use normal browser
   login and protected storage. Do not invent that entry on releases lacking it;
   return `guided_entry_unavailable` with the observed version and supported
   next action. Do not turn a failed guided entry into a bearer-grant command.
5. For an issued portal prompt, execute its exact supported setup once in the
   actual agent session. Keep its owned process attached through browser approval
   and final receipt. On missing prerequisites, expiry, refusal or interruption,
   retain the typed result and reconcile effects before any retry.

## Establish Identity and Role

Read the authenticated identity and organization through the connected Fabric
identity tool or the released client's normal supported identity/status surface.
Check active accepted membership, exact organization ID/display name, device and
endpoint attribution where available. A successful OAuth read is not enrollment
or a persistent relay.

Use the **assigned effective role and signed policy**, not the role requested in
the prompt. Keep organization membership, logical-agent identity, endpoint role
metadata, provider session and execution authority distinct. A label such as
Planner, Implementer, Reviewer or Verifier grants no permissions. Do not create
accounts, register another endpoint, change roles or give yourself administrator
access as a setup shortcut.

Require the applicable contract revision and boundaries: commands/tools, readable
and writable paths, network, disclosure, expiry and spend. Ask the authorized
owner for a specific missing decision; never substitute an API credential with
broader permissions or query a denied inventory through another actor.

## Connect Shared Knowledge First

No personal GitHub account or source checkout is intrinsically required to use
organization-authorized knowledge. Prefer the qualified knowledge-only or OAuth
route when that is the requested capability. Verify the existing shared binding,
signed manifest and catalog, recipient scope and active skill installation using
its own receipts. Do not initialize a second source or claim a persistent
knowledge-only client from a successful catalog read.

Coding access is a **separate optional scope**. Connect only the exact authorized
repository and paths. A knowledge recipient cannot scan source, write code or
publish candidates merely because it received a bundle. If the available release
offers only a source-connected setup prompt, stop the knowledge-only enrollment
at that precise gate; do not require personal GitHub access or silently clone an
unrelated repository.

## Use the Existing Factory Within the Role

Follow [Role-Bounded Work](references/role-bounded-work.md) after setup, not during
trusted enrollment authority:

- Plan from the actual task, evidence, contract and requested outcome.
- Build only where effective task authority permits writes.
- Review with bounded read access; keep setup privileges out of peer turns.
- Verify actual effects independently where the task requires it.

Use existing Fabric task, message, evaluation and signed-release workflows.
Do not build a second orchestrator or treat message delivery as execution. A
cross-client handoff must preserve sender, intended target/session, task/context
references, scope, expiry and answer attribution without exporting private history.

Use the worker's signed local rules, vocabulary, skills and permitted deterministic
checks before relevant work. Do not claim that all orchestration, analysis or
learning is model-free. A local check needs no extra inference only when its
actual implementation is deterministic.

Observation, accepted learning, validation, signed release, activation and later
use are separate states. Keep each worker's durable observation count and actual
automatic 100-boundary workflow receipts when that capability is qualified.
Do not reset counters, admit imported history as native observations, manually
substitute a batch, activate an unvalidated candidate or claim a continuous loop
from this skill's instructions. Preserve failed candidates and rollback evidence.

## Verify and Recover

Return a sanitized readiness matrix using **passed, failed, blocked or not run**:
identity/membership; assigned role/policy; protected storage; provider/session;
shared binding; signed manifest/catalog and skills; current relay/poll/startup;
task/answer and observed outcome; learning disposition; distribution/later use;
restart/offline recovery; scoped rejection; and independent rehearsal when required.

Include versions, scope, verification timestamp, receipt/correlation IDs, public
hashes, typed blocker and the supported next action. Installation, compilation,
enrollment, an acknowledgement or a healthy portal alone cannot establish full
readiness. Never include keys, grants, passwords, tokens, cookies or raw private
transcripts in the matrix.

Use only the released cause-specific recovery for the same accepted identity.
Do not edit trust files, remove locks manually, reuse expired/consumed references,
weaken sandboxing, store passwords in files or restart unrelated services. Preserve
the previous qualified release and failed receipts. If normal controls are denied,
stop at the exact boundary rather than changing wrappers, accounts or credentials.

Before claiming this skill is releasable for another provider, inspect the exact
source/artifact and real guide-use evidence in the supplied qualification record.
Static validation or a Codex rehearsal cannot prove a non-Codex customer route.
